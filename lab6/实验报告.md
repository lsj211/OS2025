# Lab6 实验报告
# 练习1：理解调度器框架的实现


### 一、调度器框架解析
- 调度类接口含义与调用时机（见 [lab6/kern/schedule/sched.h](lab6/kern/schedule/sched.h)）
	- `init(rq)`: 启动时初始化运行队列；由 `sched_init()` 调用。
	- `enqueue(rq, proc)`: 将 runnable 进程放入队列；在 `schedule()` 把当前进程重新入队或 `wakeup_proc()` 把被唤醒进程入队时调用。
	- `dequeue(rq, proc)`: 从队列移除指定进程；在 `schedule()` 选出下一个进程后立刻调用。
	- `pick_next(rq)`: 选择下一运行进程；在 `schedule()` 中调用，算法核心差异体现在这里。
	- `proc_tick(rq, proc)`: 时钟中断中对当前进程做时间片/优先级等更新；由 `run_timer_list()` 调用。
	- 采用函数指针而非直接调用，是为了把“框架”与“策略”解耦：框架只知道有这些动作，不关心数据结构（链表/堆）和策略（RR/stride），因此切换算法只需替换一套回调而无需改框架代码。

- 框架函数的解耦作用（见 [lab6/kern/schedule/sched.c](lab6/kern/schedule/sched.c)）
	- `sched_init()`: 选择默认调度类 `default_sched_class`，设置 `max_time_slice`，并调用调度类的 `init` 完成运行队列初始化。
	- `wakeup_proc()`: 负责把睡眠/阻塞进程变为 runnable 并入队，通过 `sched_class_enqueue()` 间接调用调度类的 `enqueue`，不依赖具体算法的队列结构。
	- `schedule()`: 统一的调度入口，先把当前 runnable 进程入队，再 `pick_next` 选出下一个并 `dequeue`，最后 `proc_run` 完成切换；所有算法差异都通过调度类回调体现，核心循环无需修改。

### 二、调度器使用流程与 need_resched 作用
- 初始化流程：内核启动时完成内存/中断初始化后，`sched_init()` 绑定 `default_sched_class`（RR），设定 `rq->max_time_slice` 并初始化 `run_queue`，随后进程创建（如 idle、init）进入 runnable 状态并按调度类入队。
- 调度运行时序（文字版流程图）：
	1) 时钟中断触发，进入 `trap` → `clock_intr` → `run_timer_list()`；
	2) `run_timer_list()` 在末尾调用 `sched_class_proc_tick(current)`，即调度类的 `proc_tick`（RR 时减少 `time_slice`，耗尽则置 `need_resched=1`）；
	3) 中断返回到内核态主循环/系统调用出口，检测到 `current->need_resched=1` 时调用 `schedule()`；
	4) `schedule()`：清除 `need_resched` → 如当前仍 runnable 则 `enqueue` → `pick_next` 取下一个 → 对该进程执行 `dequeue` → 若无可运行进程则选择 `idleproc` → 调用 `proc_run` 完成上下文切换；
	5) 新的 `current` 开始运行，周而复始。
- `need_resched` 的作用：它是“延迟切换”标志，保证在中断/异常返回的安全点再执行 `schedule()`，避免在硬件栈或锁持有期直接切换导致状态不一致。

### 三、调度算法切换机制
- 若要新增调度算法（如 stride）：
	1) 在 `kern/schedule/` 下实现新的调度类文件，定义一组 `init/enqueue/dequeue/pick_next/proc_tick`；
	2) 在 `default_sched_class` 处或 `sched_init()` 中把 `sched_class` 指针改为新的调度类；
	3) 运行队列字段如需要新增（如 stride 的 `lab6_run_pool`、`lab6_stride`、`lab6_priority`）可在 `run_queue` 或 `proc_struct` 中扩展，不影响框架其他部分。
- 之所以切换成本低，是因为框架的所有调用点都集中在函数指针上：策略替换只改指针，不必改 `schedule()` / `wakeup_proc()` / 中断处理流程；编译时选择不同调度类即可实现策略切换。

# 练习2：实现 Round Robin 调度算法

### 一、与 Lab5 的差异分析
- 对比调度入口 `schedule`：Lab5 的实现直接在全局进程链表上线性寻找下一个可运行进程，缺少时间片概念，见 [lab5/kern/schedule/sched.c#L26-L58](lab5/kern/schedule/sched.c#L26-L58)。Lab6 则引入调度类与运行队列抽象，在 [lab6/kern/schedule/sched.c#L17-L113](lab6/kern/schedule/sched.c#L17-L113) 中通过 `sched_class` 回调完成入队/出队/取下一个进程，同时在时钟中断里调用 `sched_class_proc_tick`。如果不做这一改动，时间片轮转等策略无法插拔，时钟无法触发重新调度，进程会长期占用 CPU，无法满足 RR 的公平性需求。

### 二、RR 各函数实现思路
- `RR_init`（[lab6/kern/schedule/default_sched.c#L18-L24](lab6/kern/schedule/default_sched.c#L18-L24)）：初始化运行队列头结点为空双向链表，清零 `proc_num` 并将 `lab6_run_pool` 置空，为后续入队做好基础状态。
- `RR_enqueue`（[lab6/kern/schedule/default_sched.c#L38-L51](lab6/kern/schedule/default_sched.c#L38-L51)）：先断言当前进程未在队列中，若时间片为 0 或超出上限则重置为 `max_time_slice`，再设置所属队列指针，用 `list_add_before` 把 `run_link` 插到队尾，并递增队列计数。
- `RR_dequeue`（[lab6/kern/schedule/default_sched.c#L60-L68](lab6/kern/schedule/default_sched.c#L60-L68)）：确保节点在队列中后使用 `list_del_init` 脱链并重新初始化节点，最后递减队列进程数，防止计数漂移。
- `RR_pick_next`（[lab6/kern/schedule/default_sched.c#L78-L88](lab6/kern/schedule/default_sched.c#L78-L88)）：从队头 `run_list.next` 获取下一个运行的节点，若队列为空返回 `NULL`，利用 `le2proc` 将链表节点转换为进程指针。
- `RR_proc_tick`（[lab6/kern/schedule/default_sched.c#L98-L109](lab6/kern/schedule/default_sched.c#L98-L109)）：每个时钟滴答将当前进程剩余时间片递减，为零时设置 `need_resched` 触发调度。时间片不会减为负值，避免出现无法重新分配的情况。

### 四、RR 调度分析
- 优点：实现简单、无饥饿，适合交互场景；缺点是频繁切换带来的开销和对长任务的吞吐影响。
- 时间片大小：时间片过小会增加上下文切换，过大则降低响应度；可根据负载特征调整 `MAX_TIME_SLICE`，例如 I/O 密集型场景可减小以提升响应，CPU 密集型可适当放大减少切换。
- `RR_proc_tick` 设置 `need_resched` 的原因：在中断上下文无法直接切换，需要标记让返回后调用 `schedule`，避免在硬件栈帧尚未收尾时进行上下文切换。

### 五、拓展思考
- 优先级 RR：可为每个优先级维护独立队列或在单队列中按优先级插入，`RR_enqueue` 按优先级选择插入位置或队列，`RR_pick_next` 优先取最高优先级的队头，时间片可与优先级成比例；`RR_proc_tick` 在时间片耗尽时降级或重新入队保持优先级顺序。
- 多核调度：当前实现仅有单个全局运行队列，不支持多核负载均衡。要支持 SMP，应为每个 CPU 维护本地 run queue，使用自旋锁保护，定期触发 load balance 将任务在核间迁移，并在 `sched_class` 中增加跨核迁移与 steal 接口以减少锁争用。

## 3. Stride Scheduling 原理概述
Stride Scheduling 属于“确定性比例份额调度”。核心思想是：
- 为每个进程分配权重（优先级）`priority`，权重越大，期望获得的 CPU 份额越多。
- 定义步长 `stride = BIG_STRIDE / priority`，`BIG_STRIDE` 为足够大的常数。
- 每次进程获得一个时间片后，更新 `pass += stride`。
- 调度器总是选择 `pass` 最小的进程运行。

因此，优先级越大，stride 越小，`pass` 增长越慢，会被更频繁地选中。

## 4. ucore 框架下的设计要点
### 4.1 数据结构与关键字段
ucore 在 `proc_struct` 中提供了 LAB6 字段：
- `lab6_stride`：当前 pass 值；
- `lab6_priority`：优先级；
- `lab6_run_pool`：用于优先队列（skew heap）的节点。

运行队列 `run_queue` 中维护：
- `lab6_run_pool`：skew heap 根指针，用于 O(log n) 取最小 stride；
- `proc_num`：就绪进程数；
- `max_time_slice`：时间片上限。

### 4.2 调度类切换
在 `sched_init` 中将 `sched_class` 切换为 `stride_sched_class`，完成 RR → Stride 的调度器替换。

### 4.3 核心流程设计（对应代码）
- **stride_init**：初始化运行队列，清空 `run_list`，`lab6_run_pool = NULL`，`proc_num = 0`。
- **stride_enqueue**：将进程插入 skew heap；校正 `time_slice`；绑定 `proc->rq` 并更新 `proc_num`。
- **stride_dequeue**：将进程从 skew heap 中移除，维护 `proc_num`。
- **stride_pick_next**：选择 `lab6_stride` 最小的进程；在返回前更新 `proc->lab6_stride += BIG_STRIDE / priority`。
- **stride_proc_tick**：时间片递减，耗尽后设置 `need_resched` 触发调度。

这一套流程保持与 ucore 的计时器/抢占机制兼容，保证调度点与时钟中断对齐。

## 5. 多级反馈队列（MLFQ）设计概要
此小节我们尝试给出 MLFQ 设计概要。可行设计如下：
- **多级队列**：设置 Q0, Q1, ... Qk，优先级逐级下降；高层队列时间片短、低层时间片长。
- **入队规则**：新进程进入最高优先级队列 Q0。
- **反馈规则**：若进程在时间片内主动让出（I/O 或阻塞），保持当前级别或提升；若耗尽时间片，则降级。
- **防止饥饿**：采用 aging（定期提升等待过久的进程）或定期“全局提升”。
- **调度选择**：总是选择非空的最高优先级队列，队列内可用 RR。

该设计能兼顾“交互性（短任务快响应）”与“吞吐量（长任务不饿死）”。

## 6. 公平性说明：为何份额 ∝ 优先级
令进程 i 的 stride 为 `S_i = BIG_STRIDE / priority_i`，其累计值为 `pass_i`。
每获得一个时间片，`pass_i` 增加 `S_i`。调度器总是选择 `pass` 最小者。

直观解释：
- 若进程 i 的 priority 更大，则 `S_i` 更小，它的 `pass_i` 增长更慢，因此更容易保持在“最小 pass”附近。
- 设进程 i 在一段时间内运行了 `T_i` 个时间片，则其累计 `pass_i ≈ T_i * S_i`。
- 调度器倾向于维持不同进程的 `pass` 在同一数量级，这意味着：
  `T_i * S_i ≈ T_j * S_j`，从而 `T_i / T_j ≈ priority_i / priority_j`。

因此，经过足够多的时间片后，各进程获得的时间片数与优先级成正比。

## 8. 小结
本次挑战实现了 Stride Scheduling 的核心机制，并与 ucore 的抢占式调度框架无缝衔接。Stride 通过“pass + stride”机制提供了可解释、可控的比例公平性；同时，通过 skew heap 保证了较好的时间复杂度。在此基础上，MLFQ 作为另一类经典调度方案，能够进一步优化交互响应与吞吐性能。
