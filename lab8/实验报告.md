
# 实验报告 Lab8

## 练习1：完成读文件操作的实现

### 打开文件的处理流程

1. `sys_open` 进入内核后调用 `sysfile_open`，先用 `copy_path` 把用户态路径拷贝到内核缓冲区。
2. `sysfile_open` 调用 `file_open`，完成：
  - 解析 `open_flags` 得到 `readable/writable`；
  - 从当前进程的文件描述符表中分配空位（`fd_array_alloc`）；
  - 调用 `vfs_open` 根据路径获得 `inode`；
  - 若 `O_APPEND` 则通过 `vop_fstat` 初始化 `file->pos`；
  - 设置 `file->node/readable/writable`，并 `fd_array_open` 标记为打开。
3. `vfs_open` 负责路径解析与创建逻辑：
  - 通过 `vfs_lookup` 查找路径；若不存在且带 `O_CREAT`，则 `vfs_lookup_parent` + `vop_create` 创建 inode；
  - 调用 `vop_open` 让具体文件系统检查打开模式；
  - `vop_open_inc` 增加打开计数；若 `O_TRUNC` 或新建则 `vop_truncate` 清空文件。
4. 在 SFS 中，`vop_lookup`/`vop_create`/`vop_open` 分别落到 `sfs_lookup*`、`sfs_create`、`sfs_openfile/sfs_opendir`，最终通过 `sfs_load_inode` 将磁盘 inode 读入内存。

### 读文件调用链

`sys_read` → `sysfile_read` → `file_read` → `vop_read` → `sfs_read` → `sfs_io` → `sfs_io_nolock`。

### sfs_io_nolock 读实现要点

- 参数校验与长度裁剪：`offset/endpos` 不合法直接返回；读操作时将 `endpos` 限制在 `din->size` 以内。
- 根据 `write` 选择读写函数指针：读文件时 `sfs_buf_op = sfs_rbuf`，`sfs_block_op = sfs_rblock`。
- 以块为单位读取，分三段处理：
  1. **首块未对齐部分**：用 `sfs_bmap_load_nolock` 映射逻辑块到磁盘块，`sfs_rbuf` 读取 `[blkoff, end)`。
  2. **中间整块**：循环读取整块，使用 `sfs_rblock`。
  3. **末块未对齐部分**：读取最后一个块的前 `endpos % SFS_BLKSIZE` 字节。
- 实际读到的长度累计到 `*alenp`；读路径不会扩展文件大小（`endpos` 已被裁剪）。

关键实现位于 `kern/fs/sfs/sfs_inode.c` 的 `sfs_io_nolock()`，读路径核心逻辑如下：

```c
blkoff = offset % SFS_BLKSIZE;
if (blkoff != 0) {
    ret = sfs_bmap_load_nolock(sfs, sin, blkno, &ino);
    size = (nblks != 0) ? (SFS_BLKSIZE - blkoff) : (endpos - offset);
    ret = sfs_buf_op(sfs, buf, size, ino, blkoff);
    // 更新 alen/buf/offset/blkno/nblks
}
while (nblks != 0) {
    ret = sfs_bmap_load_nolock(sfs, sin, blkno, &ino);
    ret = sfs_block_op(sfs, buf, ino, 1);
    // 更新 alen/buf/offset/blkno/nblks
}
if (offset < endpos) {
    ret = sfs_bmap_load_nolock(sfs, sin, blkno, &ino);
    ret = sfs_buf_op(sfs, buf, endpos - offset, ino, 0);
    // 更新 alen
}
```

### 打开文件到读的完整流程

1. 用户态 `open()` → `sys_open()` → `syscall(SYS_open, ...)` 触发 `ecall`，进入 `trap`：`exception_handler` 识别 `CAUSE_USER_ECALL` 并调用内核 `syscall()` 分发。
2. 内核 `sys_open` → `sysfile_open` 复制路径 → `file_open` 分配 `fd` 与 `file` 结构 → `vfs_open` 完成路径查找/打开：
  - `vfs_lookup` 进入具体文件系统；
  - SFS 通过 `sfs_lookup`/`sfs_load_inode` 读出 inode；
  - `vop_open` 落到 `sfs_openfile`/`sfs_opendir` 做打开检查；
  - 返回 `fd` 给用户态。
3. 用户态 `read(fd, buf, len)` → `sys_read()` → `syscall(SYS_read, ...)` → `ecall` → `sys_read` → `sysfile_read`。
4. `sysfile_read` 做权限检查与内核缓冲区分块读取：循环调用 `file_read`。
5. `file_read` 基于 `file->pos` 构造 `iobuf`，调用 `vop_read`：
  - SFS 路径：`sfs_read` → `sfs_io` → `sfs_io_nolock`；
  - `sfs_io_nolock` 通过 `sfs_bmap_load_nolock` 找物理块，使用 `sfs_rbuf/sfs_rblock` 读数据；
  - 返回实际读取长度后，`file->pos` 更新。
6. `sysfile_read` 将内核缓冲区数据 `copy_to_user` 到用户 `buf`，直到读完或遇到 EOF/错误。

### 简单说是为了解耦和可扩展：

1、VFS：统一入口/通用逻辑（路径解析、权限/flag 处理、引用计数），上层只认这一套接口。
2、VOP：抽象操作表（函数指针），实现“多态”派发到具体文件系统或设备节点。
3、SFS：具体文件系统实现（磁盘格式、inode/目录项、块映射、读写细节）。

### 简要说：

磁盘上的 inode（struct sfs_disk_inode）存的是文件元数据：

type（文件/目录/链接）
nlinks（硬链接数）
size（文件大小）
blocks（已分配的数据块数）
direct[]（直接块号数组）
indirect（一级间接块号）
内存里的 inode（struct inode + struct sfs_inode）除了上述元数据，还加了运行时信息：

inode_ops（vop_* 函数表）
ref_count/open_count
in_fs（所属文件系统）
sem/dirty/reclaim_count 等用于同步和回写的状态



# Challenge1 报告：完成基于“UNIX的PIPE机制”的设计方案

## 1. 任务理解与背景

管道（pipe）是 UNIX 进程间通信的基础机制之一，提供单向、字节流式的通信通道。用户态常见用法是 shell 通过“|”把前一进程的标准输出连接到后一进程的标准输入。对内核而言，pipe 是一对文件描述符（读端与写端）共享的一段内核缓冲区，并需要在并发访问、阻塞/唤醒、端点关闭等方面满足 POSIX 语义。

本实验要求在 ucore 现有文件系统框架内设计 pipe 的数据结构与接口语义，并重点体现对同步互斥问题的处理。由于仅要求设计方案，不需要完整实现，因此需要把“应当如何挂接到 ucore 的 VFS/文件表”讲清楚，并说明关键算法和边界条件。

## 2. 结合实验框架的系统视角分析

我们的ucore 的文件访问路径是“系统调用 → sysfile_* → file_* → VFS/inode 操作”。在现有代码中：
- `struct file`（`kern/fs/file.h`）包含 `readable/writable`、`node`、`pos`、`open_count`，适合表达 pipe 读写端的权限属性。
- `struct inode` 与 `inode_ops`（`kern/fs/vfs/inode.h`）抽象了文件对象的具体操作，适合新增 “pipe inode 类型”。
- 同步机制方面提供 `wait_queue_t` 和 `semaphore_t`（`kern/sync/wait.h`、`kern/sync/sem.h`），并在设备输入驱动中有阻塞/唤醒的范式（`dev_stdin.c`）。
- `sysfile_pipe` 在框架中尚未实现，说明设计应明确：pipe 由系统调用创建，并返回两个 fd；读写通过 VFS 的 `vop_read/vop_write` 完成。

因此，一个合理的设计是：在 VFS 层引入 pipe 类型 inode，`file_pipe()` 负责生成 pipe inode 并分配两个 file 表项；读写逻辑集中在 pipe inode 的 `vop_read/vop_write` 中；阻塞与唤醒通过 wait queue 实现。

## 4. 需求细化与语义约束
结合 POSIX 规范与实验框架，可明确以下语义要求：
1. **单向性**：pipe 有独立读端与写端，读端不可写、写端不可读。
2. **阻塞/唤醒**：
   - 读端在缓冲区为空时阻塞；若没有写端则返回 0（EOF）。
   - 写端在缓冲区满时阻塞；若没有读端则返回错误，并在支持信号时触发 SIGPIPE。
3. **原子性**：当 `n <= PIPE_BUF` 时，写端必须等待直到可用空间满足 `PIPE_BUF - count >= n`，并在一次持锁区间内写完 `n` 字节，保证不与其他写者交错；否则就阻塞等待（或非阻塞返回 `-E_AGAIN`）。
4. **非阻塞**：`read(O_NONBLOCK)` 若已有数据则返回已读字节数；只有在无数据时才返回 `-E_AGAIN`。`write(O_NONBLOCK)` 若有空间则尽量写入并返回写入量；只有在完全无空间时才返回 `-E_AGAIN`。
5. **与进程模型匹配**：在 `fork/dup` 后，读写端共享同一 pipe 结构，`readers/writers` 计数应能正确反映引用数量。

## 5. 核心数据结构设计（C 结构体）
```c
#define PIPE_BUF PGSIZE   // 以页大小作为缓冲区容量（>= POSIX 要求的 512）

typedef struct pipe_inode_info {
    char *buf;            // 环形缓冲区（内核页）
    size_t head;          // 写入位置
    size_t tail;          // 读取位置
    size_t count;         // 当前已有数据字节数
    int readers;          // 当前读端引用数
    int writers;          // 当前写端引用数
    wait_queue_t rwait;   // 读等待队列
    wait_queue_t wwait;   // 写等待队列
    semaphore_t lock;     // 互斥保护
    uint32_t flags;       // 如 O_NONBLOCK 等标志
} pipe_inode_info_t;

```
设计解释：
- `head/tail/count` 构成环形缓冲区，逻辑简单、空间利用率高。
- `readers/writers` 用于判定 EOF 与 EPIPE 条件（关键语义点）。
- `rwait/wwait` 与 ucore 的等待队列机制一致，可直接复用已有同步原语。
- `lock` 用于保护缓冲区与计数的并发访问；在 ucore 中可以用 `semaphore_t`，必要时可在临界区使用 `local_intr_save/restore` 进一步保证原子性。

## 6. 接口设计与 VFS 挂接
建议提供如下接口（语义描述为主）：
- `int sys_pipe(int fd[2]);`  
  创建匿名管道，返回读端 `fd[0]` 与写端 `fd[1]`。需要在 file 表中分配两个条目，并关联到同一 pipe inode。
- `int file_pipe(int fd[2]);`  
  内核层封装：创建 pipe inode、分配缓冲页、初始化计数和等待队列、填充两个 file 结构（readable/writable）。
- `vop_read/vop_write`  
  按字节流语义读写，忽略文件偏移 `pos`，并遵循阻塞/非阻塞规则。
- `vop_close/vop_reclaim`  
  关闭时更新 `readers/writers`，并唤醒对端等待队列，最后释放缓冲页。
- `vop_tryseek`  
  对 pipe 返回 `-E_INVAL`（不支持随机寻址）。

可选扩展：
- `sys_pipe2(int fd[2], int flags)` 便于直接设置 `O_NONBLOCK`。
- `sys_mkfifo(const char *name, uint32_t mode)` 复用 pipe inode 读写逻辑，用于命名管道。

## 7. 关键算法与流程说明
### 7.1 创建流程
1. `sys_pipe` 申请一个 pipe inode，分配一页缓冲区。
2. 初始化 `head/tail/count=0`，`readers=1`、`writers=1`。
3. 在 file 表中分配两个条目：读端 `readable=1,writable=0`，写端相反。
4. 返回两个 fd 给用户态。

### 7.2 读流程
```c
pipe_read(len):
  while (len > 0):
    if (count == 0):
       if (writers == 0) return 0;        // EOF
       if (O_NONBLOCK) return -E_AGAIN;
       sleep on rwait; continue;
    read from buf[tail], update tail/count
    wakeup wwait
```
补充：在 `O_NONBLOCK` 下，若 `count > 0` 则读出 `min(len, count)` 并直接返回；只有在 `count == 0` 时才返回 `-E_AGAIN`。

### 7.3 写流程
若 `n <= PIPE_BUF`，则写端必须等待直到 `PIPE_BUF - count >= n`，并在一次持锁区间内写完 `n` 字节；否则阻塞等待（或非阻塞返回 `EAGAIN`）。
```c
pipe_write(len):
  while (len > 0):
    if (count == PIPE_BUF):
       if (readers == 0) return -E_PIPE;  // 可能触发 SIGPIPE
       if (O_NONBLOCK) return -E_AGAIN;
       sleep on wwait; continue;
    write to buf[head], update head/count
    wakeup rwait
```
补充：在 `O_NONBLOCK` 下，若当前可用空间 `PIPE_BUF - count > 0`，则尽量写入并返回写入量；只有在完全无空间时才返回 `-E_AGAIN`。

### 7.4 关闭流程
- 读端关闭：`readers--`，若变为 0，唤醒写端，让写端返回 EPIPE。
- 写端关闭：`writers--`，若变为 0，唤醒读端，让读端返回 EOF。
- 最后一个端点关闭后释放缓冲区。

## 8. 同步互斥问题分析与处理
1. **互斥保护**：`head/tail/count` 更新必须在互斥区完成，避免并发写导致数据覆盖或计数错误。
2. **睡眠/唤醒的竞态**：必须采用“条件检查 + 循环等待”的写法，避免“先唤醒后入队”的丢失唤醒问题。即读取/写入都应在 while 循环中重新检查条件。
3. **锁与调度的配合**：在进入 sleep 前需要释放锁，否则会导致其他进程无法推进；醒来后重新获取锁再检查条件。
4. **端点关闭与阻塞进程**：当 `readers` 或 `writers` 变为 0 时，应唤醒对端等待队列，确保阻塞进程不会永久挂起。

这种策略与 `dev_stdin.c` 中“wait + schedule + wakeup”的风格一致，便于在 ucore 中落地。

## 9. 设计取舍与可扩展性说明
- **简化实现**：使用单页环形缓冲即可满足教学需求，复杂度低；与 Linux 0.12 一致，便于理解与实现。
- **可扩展方向**：
  - 支持 `pipe_buffer` 队列以扩展容量（参考现代 Linux）。
  - 增加 `poll/select` 等事件通知机制。
  - 与权限、命名管道、文件系统权限模型结合。


## 10. fork/dup/dup2 对 pipe 语义与引用计数的影响
在 ucore 中，`fork` 会复制进程的文件表，`dup/dup2` 会复制文件描述符条目。对于 pipe，这些操作会直接影响 `readers/writers` 计数，因此必须在设计中体现：

- **fork**：子进程继承父进程的 file 表，每个 pipe 端点的引用数应增加。设计上可在复制 file 表时，对 pipe inode 的 `readers/writers` 做对应自增，以保证“最后关闭的端点”才能触发 EOF/EPIPE。

- **dup/dup2**：
  1) 若 `dup`/`dup2` 复制的是读端 fd，则 `readers++`；复制写端 fd 则 `writers++`。
  2) `dup2(newfd)` 若 `newfd` 已打开，应先关闭旧 fd（从而减少计数），再复制（增加计数）。
  3) 当 `dup2(oldfd, oldfd)` 时不应改变计数。
- **语义后果**：只要仍有任意写端存在，读端空读应阻塞而非 EOF；只有最后一个写端关闭，读端才返回 EOF。相应地，只有最后一个读端关闭，写端才触发 EPIPE/SIGPIPE。该逻辑依赖 `readers/writers` 计数正确维护。

## 11. 与 Linux 资料的对应
- man7 `pipe(7)` 的语义是本设计的“规范层依据”，确保行为与 POSIX 一致。
- Linux 0.12 的 `pipe.c` 为“可实现性”提供了直接模板：页级环形缓冲 + 读写等待队列。
- 现代 Linux `pipe_inode_info` / `pipe_buffer` 结构体现了“设计演进路线”，说明本设计虽简化，但概念上兼容主流实践。

## 12. 小结
我们的设计方案明确了 pipe 在 ucore 的落点（VFS/inode + file 表），给出了可实现的结构体与核心算法，并对同步互斥的关键问题（竞态、阻塞唤醒、端点关闭）做了完整分析。









# challenge 2：在 uCore 中加入 UNIX 的硬链接与软链接机制

#### 1. 目标与范围

本设计目标是在 uCore 的 VFS/SFS 文件系统框架内加入与 UNIX/Linux 语义一致的：

- **硬链接（hard link）**：多个目录项（path 名字）指向同一个 inode；增加/减少 link count，不复制数据。
- **软链接（symbolic link / symlink）**：创建一个“内容为目标路径字符串”的特殊文件；路径解析时按规则跟随链接。

仅要求给出需要新增（或扩展）的 **数据结构** 与 **接口/语义**，并说明关键原理与同步互斥策略；不要求具体编码实现。

#### 2. uCore 现有框架与可复用点（与本设计的结合）

uCore(lab8) 已具有分层文件系统结构：

- **sysfile 层**：把用户指针拷贝到内核，再调用 VFS（例如 `sysfile_open`）。
- **file 层**：管理 fd 与 `struct file`（记录 `pos`、`inode*` 等）。
- **VFS 层**：提供 `vfs_open/vfs_lookup/...` 等对路径的抽象操作，但 `vfs_link/vfs_symlink/vfs_readlink/vfs_unlink` 目前为 `-E_UNIMP`。
- **inode 抽象**：`struct inode` + `struct inode_ops`（当前只包含 `open/read/write/lookup/create/...` 等），缺少 link/symlink/readlink/unlink 类操作。
- **SFS（simple fs）**：磁盘 inode 已含 `type` 和 `nlinks` 字段（`struct sfs_disk_inode`），并预留了 `SFS_TYPE_LINK`；且 `struct sfs_fs` 里已有 `mutex_sem`（注释写明用于 link/unlink/rename）与 `struct sfs_inode.sem`（保护 din）。

因此：

1) 设计上应当把“链接语义”放在 VFS/inode 层抽象接口中；
2) 把具体落盘的 `nlinks/type/目录项` 更新交给 SFS 实现；
3) 同步互斥优先复用 SFS 已有的 `mutex_sem` 与 per-inode `sem`。

#### 3. 核心语义（对齐 UNIX/Linux）

##### 3.1 硬链接语义（参考 POSIX `link(2)`）

- `link(oldpath, newpath)`：
  - 目标效果：在 `newpath` 所在目录新增一个目录项 `basename(newpath)`，指向 `oldpath` 对应的同一个 inode。
  - `newpath` 不能已存在；硬链接通常不允许链接目录（避免循环），本设计同样禁止。
  - `oldpath` 与 `newpath` 必须在同一挂载/同一文件系统（SFS 内）。
- 影响：inode 的 `nlinks++`；数据块不复制。

##### 3.2 删除语义（参考 POSIX `unlink(2)`）

- `unlink(path)` 删除一个目录项。
- 若被删除目录项指向普通文件：inode 的 `nlinks--`。
- **关键语义**：当 `nlinks == 0` 且**没有进程仍打开该文件**时，才真正释放 inode 与数据块；否则文件内容继续存在，直到最后一个 fd 关闭。

##### 3.3 软链接语义（参考 POSIX `symlink(2)`/`readlink(2)`）

- `symlink(target, linkpath)` 创建一个类型为 symlink 的 inode，并把字符串 `target` 作为该 inode 的内容。
  - 不检查 `target` 是否存在（允许 dangling link）。
- `readlink(linkpath, buf, bufsiz)` 读取 symlink 的内容字符串：
  - **返回写入字节数**；不自动追加 `\0`；缓冲区不足时允许截断。

##### 3.4 路径解析与 symlink 跟随规则（namei 思想）

- 默认解析路径时会跟随 symlink（尤其是中间路径分量）。
- 应支持一个基本开关：
  - **跟随最后分量**（open/exec 等常用路径）
  - **不跟随最后分量**（lstat/readlink/open(O_NOFOLLOW) 等）
- 必须限制递归深度：`SYMLINK_MAX`（Linux 常见为 40），超过返回 `-E_LOOP`。

#### 4. 至少需要新增/扩展的数据结构（给出 C struct 定义）

下面给出“在 uCore 现有结构上最小侵入”的设计：主要扩展 inode 抽象与引入路径解析状态。

##### 4.1 VFS 层：路径解析状态（nameidata）

```c
// 解析路径时的上下文：控制是否跟随 symlink、递归深度等
typedef struct vfs_nameidata {
    int follow_symlinks;      // 1: 默认跟随; 0: 不跟随(用于 lstat/readlink 等)
    int follow_last;          // 1: 跟随最后分量; 0: 不跟随最后分量
    int symlink_depth;        // 当前已跟随次数
    int symlink_max;          // 上限，建议 40
} vfs_nameidata_t;
```

说明：uCore 当前没有 dentry cache；本设计不强制引入 dentry，只引入一个最小的 namei 状态结构即可实现正确的跟随规则与深度限制。

##### 4.2 inode 抽象扩展：补齐链接相关 inode 操作

uCore 当前 `struct inode_ops` 缺少 link/symlink/readlink/unlink 等操作。最小扩展如下：

```c
struct inode_ops {
    unsigned long vop_magic;
    /* ...已有的 vop_open/vop_read/vop_write/vop_lookup/vop_create 等... */

    // 在目录 inode 上：创建目录项 name，指向 target inode（硬链接）
    int (*vop_link)(struct inode *dir, const char *name, struct inode *target);

    // 在目录 inode 上：删除目录项 name（unlink）；是否释放 inode 由 nlinks/open_count 决定
    int (*vop_unlink)(struct inode *dir, const char *name);

    // 在目录 inode 上：创建一个 symlink 目录项 name，其 inode 内容为 target_path
    int (*vop_symlink)(struct inode *dir, const char *name, const char *target_path);

    // 在 symlink inode 上：读取 target_path 到 iobuf；不追加 '\0'
    int (*vop_readlink)(struct inode *link_node, struct iobuf *iob);
};
```

说明：

- `link/unlink/symlink` 都是“修改目录项”的操作，因此接口放在 **目录 inode** 上最自然。
- `readlink` 是“读取 symlink 内容”，因此接口放在 **symlink inode** 上。

##### 4.3 SFS 落盘与内存态关键字段（复用现有结构）

SFS 已有：

- `struct sfs_disk_inode { uint16_t type; uint16_t nlinks; ... }`
- `SFS_TYPE_LINK`
- `struct sfs_fs { semaphore_t mutex_sem; }`（用于 link/unlink/rename）

本设计保持 `SFS_TYPE_LINK` 作为 symlink：其“文件内容”即 `target_path` 字符串（存放在 data blocks；小目标路径可选做 inline 优化，但非必须）。

##### 5.3 file 层 / open 层的 symlink 处理

建议在 `vfs_open` 的路径解析阶段支持：

- 默认跟随 symlink；
- 若传入 `O_NOFOLLOW`，则最后分量是 symlink 时返回 `-E_LOOP`（与 Linux 行为一致：`open(O_NOFOLLOW)` 在 trailing component 为 symlink 时失败）。

#### 6. 关键实现原理（概要）

##### 6.1 硬链接为什么“只改目录项 + nlinks”？

在 UNIX 模型里：

- **inode 表示文件实体**（数据块、大小、权限、link count 等）。
- **目录项（dir entry）只是 name → inode 的映射**。

因此硬链接就是新增一个 name 指向同一 inode，并将 inode 的 link count 增加。删除某个名字只是删除一个映射并减少 link count。

##### 6.2 为什么 unlink 后文件可能仍存在？

`unlink(2)` 的经典语义：

- 如果这是最后一个名字且没人打开，才真正释放。
- 如果有人打开，则 inode 仍被 open file description（uCore 的 `struct file`/`inode` 引用计数）持有，等最后一次 close 才回收。

在 uCore 中，可用：

- inode 的 `open_count` / `ref_count` 反映“仍被使用”；
- SFS 的 `nlinks` 反映“仍有目录项名字”。

最终释放条件可以设计为：`nlinks==0 && open_count==0 && ref_count==0`（或等价条件）。

##### 6.3 软链接为什么需要 namei/递归深度限制？

symlink 的本质是“把路径字符串嵌入到一个 inode 中”。路径解析（namei）遇到 symlink 时，需要把 symlink 的内容替换进路径继续解析。

为了防止 `a -> b, b -> a` 这种循环，必须限制跟随次数，超过上限返回 `-E_LOOP`。

#### 7. 同步互斥与一致性：可能的竞态与处理策略

链接相关操作会同时修改：

- 目录数据（新增/删除目录项）
- inode 元数据（`nlinks`、时间戳、可能的 size 等）

因此要考虑并发下的原子性与死锁。

##### 7.1 推荐的锁粒度与锁顺序

- **文件系统全局互斥（每个 FS 实例）**：复用 SFS 的 `sfs->mutex_sem`，把 link/unlink/rename 这种“多对象元数据更新”串行化，降低实现复杂度并避免目录项与 nlinks 不一致。
- **inode 互斥（每个 inode）**：复用 `sfs_inode.sem` 保护对 `din` 的修改（nlinks/type/size/blocks 等）。

锁顺序建议：

1) `down(sfs->mutex_sem)`（整个操作期间持有，保证目录项与 nlinks 更新的原子性）
2) `down(dir_inode->sem)`（修改目录内容）
3) 若需要同时修改 target inode（硬链接需要 `nlinks++`，unlink 需要 `nlinks--`），则再 `down(target_inode->sem)`
4) 释放顺序相反。

避免死锁的细节：

- 多 inode 加锁时按稳定顺序（例如 inode number 从小到大）上锁。
- rename/link 涉及两个目录时，也按“目录 inode number 排序”加锁。

##### 7.2 典型竞态举例

- **并发 link/unlink 导致 nlinks 错乱**：若不做互斥，两个线程同时 `nlinks++`/`--` 可能丢失更新。解决：`sfs_inode.sem` 或更高层 `mutex_sem` 序列化。
- **unlink 与 open/close 并发导致提前释放**：必须把“是否释放数据块”的判定放在持锁区间，并与 open_count/ref_count 的变化协调。
- **symlink 跟随与并发修改**：readlink/解析时读取到的 target 字符串可能被并发修改（若允许修改 symlink 内容）。简化起见：symlink 内容在创建后不可变（常见语义），则只需保证读取一致（inode 读锁）。

#### 8. 设计与 Linux/UNIX 资料的对应关系（概要引用）

本设计遵循 POSIX/Linux 常见语义：

- `link(2)`：硬链接创建，不覆盖 `newpath`，一般不允许链接目录；跨文件系统返回 EXDEV。
- `unlink(2)`：删除名字；若是最后一个链接且无打开引用才真正删除。
- `symlink(2)`：创建内容为 target 字符串的 symlink；允许 dangling。
- `readlink(2)`：读取 symlink 内容，不追加 `\0`，可能截断。
- `open(2)`：支持 `O_NOFOLLOW`（最后分量为 symlink 时失败，报 ELOOP）。

参考阅读：Linux man-pages（`link(2)`, `unlink(2)`, `symlink(2)`, `readlink(2)`, `open(2)`）与“namei/path resolution”相关文档。
