## Lab8 实验报告

### challenge 2：在 uCore 中加入 UNIX 的硬链接与软链接机制（设计方案）

#### 1. 目标与范围

本设计目标是在 uCore 的 VFS/SFS 文件系统框架内加入与 UNIX/Linux 语义一致的：

- **硬链接（hard link）**：多个目录项（path 名字）指向同一个 inode；增加/减少 link count，不复制数据。
- **软链接（symbolic link / symlink）**：创建一个“内容为目标路径字符串”的特殊文件；路径解析时按规则跟随链接。

仅要求给出需要新增（或扩展）的 **数据结构** 与 **接口/语义**，并说明关键原理与同步互斥策略；不要求具体编码实现。

#### 2. uCore 现有框架与可复用点（与本设计的结合）

uCore(lab8) 已具有分层文件系统结构：

- **sysfile 层**：把用户指针拷贝到内核，再调用 VFS（例如 `sysfile_open`）。
- **file 层**：管理 fd 与 `struct file`（记录 `pos`、`inode*` 等）。
- **VFS 层**：提供 `vfs_open/vfs_lookup/...` 等对路径的抽象操作，但 `vfs_link/vfs_symlink/vfs_readlink/vfs_unlink` 目前为 `-E_UNIMP`。
- **inode 抽象**：`struct inode` + `struct inode_ops`（当前只包含 `open/read/write/lookup/create/...` 等），缺少 link/symlink/readlink/unlink 类操作。
- **SFS（simple fs）**：磁盘 inode 已含 `type` 和 `nlinks` 字段（`struct sfs_disk_inode`），并预留了 `SFS_TYPE_LINK`；且 `struct sfs_fs` 里已有 `mutex_sem`（注释写明用于 link/unlink/rename）与 `struct sfs_inode.sem`（保护 din）。

因此：

1) 设计上应当把“链接语义”放在 VFS/inode 层抽象接口中；
2) 把具体落盘的 `nlinks/type/目录项` 更新交给 SFS 实现；
3) 同步互斥优先复用 SFS 已有的 `mutex_sem` 与 per-inode `sem`。

#### 3. 核心语义（对齐 UNIX/Linux）

##### 3.1 硬链接语义（参考 POSIX `link(2)`）

- `link(oldpath, newpath)`：
  - 目标效果：在 `newpath` 所在目录新增一个目录项 `basename(newpath)`，指向 `oldpath` 对应的同一个 inode。
  - `newpath` 不能已存在；硬链接通常不允许链接目录（避免循环），本设计同样禁止。
  - `oldpath` 与 `newpath` 必须在同一挂载/同一文件系统（SFS 内）。
- 影响：inode 的 `nlinks++`；数据块不复制。

##### 3.2 删除语义（参考 POSIX `unlink(2)`）

- `unlink(path)` 删除一个目录项。
- 若被删除目录项指向普通文件：inode 的 `nlinks--`。
- **关键语义**：当 `nlinks == 0` 且**没有进程仍打开该文件**时，才真正释放 inode 与数据块；否则文件内容继续存在，直到最后一个 fd 关闭。

##### 3.3 软链接语义（参考 POSIX `symlink(2)`/`readlink(2)`）

- `symlink(target, linkpath)` 创建一个类型为 symlink 的 inode，并把字符串 `target` 作为该 inode 的内容。
  - 不检查 `target` 是否存在（允许 dangling link）。
- `readlink(linkpath, buf, bufsiz)` 读取 symlink 的内容字符串：
  - **返回写入字节数**；不自动追加 `\0`；缓冲区不足时允许截断。

##### 3.4 路径解析与 symlink 跟随规则（namei 思想）

- 默认解析路径时会跟随 symlink（尤其是中间路径分量）。
- 应支持一个基本开关：
  - **跟随最后分量**（open/exec 等常用路径）
  - **不跟随最后分量**（lstat/readlink/open(O_NOFOLLOW) 等）
- 必须限制递归深度：`SYMLINK_MAX`（Linux 常见为 40），超过返回 `-E_LOOP`。

#### 4. 至少需要新增/扩展的数据结构（给出 C struct 定义）

下面给出“在 uCore 现有结构上最小侵入”的设计：主要扩展 inode 抽象与引入路径解析状态。

##### 4.1 VFS 层：路径解析状态（nameidata）

```c
// 解析路径时的上下文：控制是否跟随 symlink、递归深度等
typedef struct vfs_nameidata {
    int follow_symlinks;      // 1: 默认跟随; 0: 不跟随(用于 lstat/readlink 等)
    int follow_last;          // 1: 跟随最后分量; 0: 不跟随最后分量
    int symlink_depth;        // 当前已跟随次数
    int symlink_max;          // 上限，建议 40
} vfs_nameidata_t;
```

说明：uCore 当前没有 dentry cache；本设计不强制引入 dentry，只引入一个最小的 namei 状态结构即可实现正确的跟随规则与深度限制。

##### 4.2 inode 抽象扩展：补齐链接相关 inode 操作

uCore 当前 `struct inode_ops` 缺少 link/symlink/readlink/unlink 等操作。最小扩展如下：

```c
struct inode_ops {
    unsigned long vop_magic;
    /* ...已有的 vop_open/vop_read/vop_write/vop_lookup/vop_create 等... */

    // 在目录 inode 上：创建目录项 name，指向 target inode（硬链接）
    int (*vop_link)(struct inode *dir, const char *name, struct inode *target);

    // 在目录 inode 上：删除目录项 name（unlink）；是否释放 inode 由 nlinks/open_count 决定
    int (*vop_unlink)(struct inode *dir, const char *name);

    // 在目录 inode 上：创建一个 symlink 目录项 name，其 inode 内容为 target_path
    int (*vop_symlink)(struct inode *dir, const char *name, const char *target_path);

    // 在 symlink inode 上：读取 target_path 到 iobuf；不追加 '\0'
    int (*vop_readlink)(struct inode *link_node, struct iobuf *iob);
};
```

说明：

- `link/unlink/symlink` 都是“修改目录项”的操作，因此接口放在 **目录 inode** 上最自然。
- `readlink` 是“读取 symlink 内容”，因此接口放在 **symlink inode** 上。

##### 4.3 SFS 落盘与内存态关键字段（复用现有结构）

SFS 已有：

- `struct sfs_disk_inode { uint16_t type; uint16_t nlinks; ... }`
- `SFS_TYPE_LINK`
- `struct sfs_fs { semaphore_t mutex_sem; }`（用于 link/unlink/rename）

本设计保持 `SFS_TYPE_LINK` 作为 symlink：其“文件内容”即 `target_path` 字符串（存放在 data blocks；小目标路径可选做 inline 优化，但非必须）。

##### 5.3 file 层 / open 层的 symlink 处理

建议在 `vfs_open` 的路径解析阶段支持：

- 默认跟随 symlink；
- 若传入 `O_NOFOLLOW`，则最后分量是 symlink 时返回 `-E_LOOP`（与 Linux 行为一致：`open(O_NOFOLLOW)` 在 trailing component 为 symlink 时失败）。

#### 6. 关键实现原理（概要）

##### 6.1 硬链接为什么“只改目录项 + nlinks”？

在 UNIX 模型里：

- **inode 表示文件实体**（数据块、大小、权限、link count 等）。
- **目录项（dir entry）只是 name → inode 的映射**。

因此硬链接就是新增一个 name 指向同一 inode，并将 inode 的 link count 增加。删除某个名字只是删除一个映射并减少 link count。

##### 6.2 为什么 unlink 后文件可能仍存在？

`unlink(2)` 的经典语义：

- 如果这是最后一个名字且没人打开，才真正释放。
- 如果有人打开，则 inode 仍被 open file description（uCore 的 `struct file`/`inode` 引用计数）持有，等最后一次 close 才回收。

在 uCore 中，可用：

- inode 的 `open_count` / `ref_count` 反映“仍被使用”；
- SFS 的 `nlinks` 反映“仍有目录项名字”。

最终释放条件可以设计为：`nlinks==0 && open_count==0 && ref_count==0`（或等价条件）。

##### 6.3 软链接为什么需要 namei/递归深度限制？

symlink 的本质是“把路径字符串嵌入到一个 inode 中”。路径解析（namei）遇到 symlink 时，需要把 symlink 的内容替换进路径继续解析。

为了防止 `a -> b, b -> a` 这种循环，必须限制跟随次数，超过上限返回 `-E_LOOP`。

#### 7. 同步互斥与一致性：可能的竞态与处理策略

链接相关操作会同时修改：

- 目录数据（新增/删除目录项）
- inode 元数据（`nlinks`、时间戳、可能的 size 等）

因此要考虑并发下的原子性与死锁。

##### 7.1 推荐的锁粒度与锁顺序

- **文件系统全局互斥（每个 FS 实例）**：复用 SFS 的 `sfs->mutex_sem`，把 link/unlink/rename 这种“多对象元数据更新”串行化，降低实现复杂度并避免目录项与 nlinks 不一致。
- **inode 互斥（每个 inode）**：复用 `sfs_inode.sem` 保护对 `din` 的修改（nlinks/type/size/blocks 等）。

锁顺序建议：

1) `down(sfs->mutex_sem)`（整个操作期间持有，保证目录项与 nlinks 更新的原子性）
2) `down(dir_inode->sem)`（修改目录内容）
3) 若需要同时修改 target inode（硬链接需要 `nlinks++`，unlink 需要 `nlinks--`），则再 `down(target_inode->sem)`
4) 释放顺序相反。

避免死锁的细节：

- 多 inode 加锁时按稳定顺序（例如 inode number 从小到大）上锁。
- rename/link 涉及两个目录时，也按“目录 inode number 排序”加锁。

##### 7.2 典型竞态举例

- **并发 link/unlink 导致 nlinks 错乱**：若不做互斥，两个线程同时 `nlinks++`/`--` 可能丢失更新。解决：`sfs_inode.sem` 或更高层 `mutex_sem` 序列化。
- **unlink 与 open/close 并发导致提前释放**：必须把“是否释放数据块”的判定放在持锁区间，并与 open_count/ref_count 的变化协调。
- **symlink 跟随与并发修改**：readlink/解析时读取到的 target 字符串可能被并发修改（若允许修改 symlink 内容）。简化起见：symlink 内容在创建后不可变（常见语义），则只需保证读取一致（inode 读锁）。

#### 8. 设计与 Linux/UNIX 资料的对应关系（概要引用）

本设计遵循 POSIX/Linux 常见语义：

- `link(2)`：硬链接创建，不覆盖 `newpath`，一般不允许链接目录；跨文件系统返回 EXDEV。
- `unlink(2)`：删除名字；若是最后一个链接且无打开引用才真正删除。
- `symlink(2)`：创建内容为 target 字符串的 symlink；允许 dangling。
- `readlink(2)`：读取 symlink 内容，不追加 `\0`，可能截断。
- `open(2)`：支持 `O_NOFOLLOW`（最后分量为 symlink 时失败，报 ELOOP）。

参考阅读：Linux man-pages（`link(2)`, `unlink(2)`, `symlink(2)`, `readlink(2)`, `open(2)`）与“namei/path resolution”相关文档。
